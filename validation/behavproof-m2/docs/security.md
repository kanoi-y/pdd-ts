# Trust and GitHub deployment

`check` reads evidence. It does not run test files, import project configuration, or load project plugins. Static declarations and local JSON are data, never approval authority. A Collector invocation runs an explicitly selected command; run candidate code in an isolated credential-free worker. Before/after hashes detect persistent input changes, not transient malicious changes restored before exit.

The trusted host must pin the verifier, policy and registry outside the candidate checkout. It supplies repository ID, immutable workflow SHA, run/attempt/job ID, selected command hash, full input/config/lock inventory and artifact inventory. Obtain approval targets from the computed registry/Intent transition, never the PR body. Fetch GitHub authority asynchronously, then pass strict synchronous membership verifiers to the deterministic libraries.

The read-only GitHub adapter needs repository metadata/contents, pull requests, actions and collaborator permission reads. Branch-protection reads require Administration: read; organization policy may require additional access. Missing access, unsupported ruleset-only protection, missing source App ID, ambiguous pagination and unsupported CI events remain `unknown`. Public repository access alone does not establish producer trust.

A workflow artifact digest authenticates downloaded archive bytes only when the caller computes that digest independently. The GitHub artifact API does not provide a cryptographic job-to-artifact binding. A pinned, protected workflow must enforce a unique run/attempt/job artifact name and prevent other jobs or candidate code from publishing it. The adapter supports trusted workflow_dispatch/workflow_run/push producers. It does not promote pull_request artifacts to trusted producers.

Use a protected verifier workflow with a credential-free candidate worker, then a separate publisher environment holding a dedicated GitHub App credential. The publisher must never check out or execute candidate code. Require the gate context **and its App ID** in branch protection. A same-name GitHub Actions check is insufficient. Protect the verifier source/ref and environment separately; a workflow in the candidate PR can be deleted or replaced. A local workflow diagnosis reports internal definition health separately from external merge protection.

Never put production credentials in candidate CI. The provided workflow template is an internal audit/gate template, not a self-establishing external trust root. It intentionally requires a separately provisioned root before gate mode can pass. Do not install it as a privileged pull_request_target workflow.

GitHub documents [expected status-check sources](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches) and [issuer-bound app_id protection](https://docs.github.com/en/rest/branches/branch-protection). Verify the actual target repository protection and test deleted/skipped/replaced gates before claiming external enforcement. Historical checks or a JSON fixture are not live BehavProof acceptance evidence.
