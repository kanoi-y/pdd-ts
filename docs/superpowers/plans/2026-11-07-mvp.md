# pdd-ts MVP Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. The user has explicitly requested implementation through MVP; execute in this chat without another design approval round.

**Goal:** Ship the Phase 0–3 MVP of the approved integrated plan and use its requirements, proof, tests and evidence on this tool itself.

**Architecture:** One TypeScript package with CLI, requirement registry, LemmaScript process adapter, fail-closed policy, external approval/CI integration and deterministic Markdown/JSON reports. Contracts live in real TS sources. Historical evidence never replaces a missing current obligation.

**Tech Stack:** Node >=22, pnpm, TypeScript, Zod, YAML, Vitest, fast-check, LemmaScript 0.6.6, Dafny 4.11.0 with bundled Z3, GitHub Actions.

**Spec:** `docs/PDD_for_TypeScript_統合実装計画.md` (MVP §§2.2, 3–4, 7–14; Phase 4+ are deferred).

## Global Constraints

- Existing TypeScript is the verified source; no independent model may be called its proof.
- AI-free CLI; Proof/Test/Trusted/Unverified stay distinguishable; unknown, unsupported, stale, missing or unapproved cannot satisfy a required proof.
- Preserve the PDD Kit motivation and approved scope. No custom contract DSL or autonomous implementer in MVP.
- Source contracts, assumptions, obligations and exemptions form the approval digest. External approval is checked, never manufactured locally.
- Tests of the actual tool come first; source proof and empirical tests remain different evidence.
- No remote exists initially. Local integration tests may emulate GitHub API responses, but must not be presented as a real human approval or hosted CI run.

## Review Focus

1. Missing/duplicate obligations, skipped or zero tests: reject instead of green on an empty result set (T04/T05).
2. Repo-relative path escape, symlinks, shell injection and hung subprocesses: contain reads/writes and kill bounded executions (T05/T06).
3. Contradictory preconditions and inserted assumptions/proof bypass: reject independently of solver success (T02/T05).
4. A fake receipt, obsolete source, other workflow or stale approval: reject against external identity and protected baseline (T08/T10).
5. Imported constants, hand proof files and changed input validators: invalidate evidence and require correct boundary evidence (T05/T09).

## Execution rules

For each task: write its behavioral tests, run and record the expected failure, implement the named interfaces, run the task checks and whole current suite, then commit and record the evidence in `docs/implementation-progress.md`. A PoC is an experiment, not production implementation. User approval of the integrated plan authorizes its mechanical implementation; new specs are derived requirements, not forged external approvals.
