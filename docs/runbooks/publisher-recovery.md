# 発行処理が自身の必須チェックを壊した場合の復旧

通常の運用で保護を迂回してはならない。今回のコピー不具合は、main自身が
必須にしている発行処理を常に失敗させるため、所有者が明示的に許可した
一度限りの復旧操作が必要になる。許可されるまでmainや保護を変更しない。

復旧用コミットは、既存mainを親とし、発行処理の修正・回帰テスト・必須登録と
対応する要件改訂だけを含む。契約式、承認者、App ID、署名・鮮度条件は変えない。
本体PRはこの復旧コミットを祖先に含め、最新headを本人がGitHubで再承認する。

許可後の手順:

1. main・復旧コミット・PRのheadを完全SHAで固定し、通常CI成功、本人の正確な
   headへの承認、復旧コミットがその祖先であることを再確認する。
2. 元の保護設定を保存する。所有者に適用される `enforce_admins` だけを一時的に
   無効化する。この間、所有者はチェック・レビューを技術的に迂回できるため、
   他の更新は一切せず、許可された復旧コミットへのfast-forwardだけを行う。
3. 成否にかかわらずfinallyで直ちに `enforce_admins` を再有効化する。必須チェック、
   発行App ID、レビュー条件、force-push・削除の禁止は書き換えない。
4. mainのSHAと保護設定の復元をAPIで確認する。架空の成功チェックは投稿しない。
5. 同じ承認済みPRのheadで、復旧後mainから通常の保護ワークフローを実行する。
   実際の署名と専用Appチェックが成功するまで、保護ゲート完成とは判定しない。

これは常設のバイパス機能でも自動復旧でもない。別の不具合や別のSHAへの許可を
意味しない。追加の例外が必要な場合は、実ログとレビューできる修正を再度提示する。
