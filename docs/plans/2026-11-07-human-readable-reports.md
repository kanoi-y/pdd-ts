# 人が次の行動を判断できる検証レポート

**根拠:** 既存実装計画 §5.3–5.5、Phase3。日本語訳後も「目的・内容が分からずレビュー資料として意味がない」という本人の実フィードバック。

**目標:** レポート単体で、対象の機能・目指す振る舞い・確認できた範囲・未解決の理由・次の担当を伝える。人に内部データの解読を依頼しない。

**設計:** 既存の要件文と契約説明を正本に使い、結果から開発側の対応を決定論的に導く。未記述の業務上の意味や変更理由を識別子から推測しない。検証不備は開発側の対応として示し、検証が揃った場合に仕様確認の依頼を示す。既存の判定・署名・外部承認条件は変更しない。

## 採用する表示

1. 何の資料か、いま仕様レビューを依頼できる段階か。
2. 対象機能と、要件に記述された振る舞い。変更前後の情報を持たない実行レポートで、振る舞いの変更を創作しない。
3. 開発側が先に対応する問題と、その理由。テスト不足・古い証拠・未説明の信頼前提を本人への盲目的な承認依頼に変換しない。
4. 実際に確認できた契約とテスト範囲。形式証明と実行したケースを区別し、アプリ全体や外部の本人情報を証明したと扱わない。
5. 人が仕様として確認すべきこと。問題が残る間は承認を求めず、内容が不明な前提は開発側の説明不足とする。
6. 完全な要件・生の診断・境界・結果・ハッシュ・根拠リンクを詳細へ保存。

単なる翻訳・全情報の列挙・IDからの自動作文は採用しない。新しいAI生成サービスや独自の仕様DSLは追加しない。最小Review Packetの既存要件を修復する。

## 実装手順

- [x] `tests/unit/report.test.ts`で、欠落したテストと未許可の前提が開発側へ返ること、ローカル成功がCI成功に見えないこと、証明対象の契約だけを説明することをREDにする。
- [x] 純粋なレポート要約処理と日本語Markdownを実装する。必須検証との対応をpacketに渡し、結果を要件に結び付ける。生の結果は詳細に残す。
- [x] このリポジトリと両サンプルの要件・契約説明を同じ意味の日本語にする。形式契約・ID・信頼条件は維持。保護された変更にはrevisionを上げ、必要なテストと新ファイルを登録する。
- [x] 実際のCLIで両サンプルと2つの負例を生成し、手作業の翻訳なしに日本語の要点と次の担当が出ることを確認する。試験用サンプルだという説明を案内へ加える。
- [ ] 型検査・全テスト・独立レビューの後、実際のPRを作る。本人レビューは最終コミットで確認し、通常の保護CIを使う。

## 検証の注意

自動テストは判定と表示の対応、範囲、欠落、根拠保持、エスケープを検査する。読みやすさや人間の負担削減を証明しない。人間による理解・導入／仕様／修正／レビュー／維持の比較は実測のまま別記録とする。
