# Phase 4: 読み取り専用調査とArchitecture Atlas

## 目的と進め方

実装計画§5.1/Phase4を進める。本人の指示により、比較試用は後日に残して独立した実装を継続する。MVP/GateP4の利用効果が実証済みとは扱わない。

- 既存のts-morphで、設定やアプリを実行せずにTypeScript/TSXをAST解析する。
- scanは.pdd初期化・Git・証明ツールを前提にせず、標準出力へJSON/日本語Markdownを返す。対象プロジェクトのファイルを作成・変更しない。
- 既存AST解析を再利用する。実行による調査、独自のAI推論サービス、既存コードの自動仕様承認は追加しない。

## 対象

1. **調査結果**: 根拠の相対パス・行・入力ハッシュ付きの関数、静的import/call、外部/動的呼び出し、ルート候補。範囲・除外・未解決箇所を明示。
2. **Atlas**: 概要、境界、最大3つの根拠付きフロー、契約/不変条件の候補、変更の波及。正常/異常の実行順や到達性を静的構文だけから確認済みにしない。
3. **適合性候補**: 純粋関数の候補と理由・制約。候補はProofでも業務仕様の承認でもない。
4. **差分**: 保存した調査JSONとの構文上の変更一覧。意味的な強化/弱化や保証を推測しない。
5. **連携**: Review PacketにAtlas更新候補を接続する。調査データをゲートの証拠や承認へ昇格しない。

## 境界

- node_modules/.git/.tools、ビルド/検証成果物を調査対象から除外し、除外範囲を出力へ記録。
- シンボリックリンクを辿らない。通常のTSファイルと許可したREADME/package/tsconfigだけを読み、環境ファイル・認証情報・実行可能設定を読まない。
- ファイル数、深さ、個別/合計バイト量、AST結果件数を制限。構文エラー・制限超過・未解決import/動的呼び出しを隠さない。
- 文書は未信頼データとしてescapeし、Mermaidの識別子は生成番号を使う。ファイル内容を命令として扱わない。

## 受け入れ条件

対象コードにpostinstallや任意関数を置いても実行されない。PDD未導入のHono構成で関数・依存・境界候補と根拠を取得でき、対象の全バイトが走査前後で同じ。静的に不明な情報、見えていない範囲、候補の不確実性が人向け出力から分かる。既存216テストと形式契約・本人承認・CI条件を維持する。
