# PR本文の読みやすさの改善

根拠は、所有者からの「日本語化しても本文が分かりにくすぎる」という実際の評価と、既存MVP計画Phase3の最小Review Packet／理解度評価である。読みやすさの効果はまだ未測定として扱う。

実装上の判断として、短い判断欄を先頭に置き、完全な仕様データを本文内で折りたたむ。詳細を別の生成ファイルだけへ移す案は、現在の固定コミット・全仕様の照合導線を増やすため採らない。表示を整理しながら完全な元データを保持する。

- 先頭に、仕様差分の有無、承認時に確認すること、必須検証の登録規模、実行結果・本人承認が未取得であることを示す。
- 追加された信頼前提、変更されたソース契約の入力前提、削除された要件／必須義務は折りたたみの外に示す。境界だけに追加された未許可の前提も見落とさない。
- 全要件・全契約・前提・モデル・必須検証・完全SHA／ダイジェストは詳細欄に保持する。エスケープと60,000byteの上限は維持する。
- ソース証明、署名、承認、App発行元、鮮度の条件は変更しない。短い本文やApproveを、人間の認知負荷削減の実証とは扱わない。

実行順序は、既存の完全性テストに先頭表示と新前提の可視性を追加して実際の失敗を確認、最小の表示変更、全件テスト／型検査、実データの前後比較と独立レビュー、通常のBot PR・本人承認・保護CIである。外部の比較試用は別途、実際の読者の回答と時間を測る。

実際の欠落テスト例では停止理由の診断が空だったため、結果に含まれない必須テスト名もレポートへ出す。unknown／不合格の扱いと件数の保守的な扱いは維持し、報告に名前がないことを未実行の断定とは区別する。実実行の回帰テストで診断欠落のREDを確認してから修正する。
